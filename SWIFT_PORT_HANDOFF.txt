Known actual identifiers:
  bikes.id: UUID; user_id UUID owns each bike.
  ride_sessions.id: UUID; bike_id UUID nullable; user_id UUID owns each session.
  ride_samples.id: bigint identity. Decode as Int64, never UUID.

All three tables use owner RLS plus a restrictive verified-permanent-user policy.
Sessions have recording/complete/cancelled status. Current migration adds nullable
client_sync_version integer and completion_applied_at timestamptz.

Types/units: timestamps UTC ISO 8601; native Date with explicit decoding strategy;
latitude/longitude decimal degrees; sample speed_mps meters/second; altitude_m and
accuracy_m meters; session distance_miles and speed fields mph; acceleration fields
follow their explicit _g or axis contract. Preserve null as unknown. Never turn
missing GPS, sensor, speed-limit or cost data into a measured zero. Historic
maintenance references may be labels while newer references are bike UUIDs.
Check every table payload in APP_INVENTORY and its owner module before mapping.

5. DURABLE RIDE PROTOCOL (WEB AND SWIFT MUST AGREE)
State progression: idle -> recording -> pending -> synced. A persisted recording
with no running capture is presented as interrupted. Discarding is a durable
cleanup intent. The active Boolean means capture is running, not upload pending.

IndexedDB database name: moto-ride-journal-v1:<backend URL origin>, schema version 1.
Stores: rides keyed [owner,id], with owner index; samples keyed [owner,rideId,sequence].
Each ride persists its bike snapshot, start/stop times, sample/ack counters,
cloud-created acknowledgement, totals, previous/latest fix, interruption intervals
and completionRequested. Each queued row has a stable client UUID.

Start acquires the exclusive capture Web Lock and commits local state before GPS.
The GPS broker still has one native watcher. Valid GPS samples are limited to one
per second and sample+summary changes commit in the same strict IDB transaction.
Optional motion shares the serialized queue. Storage failure visibly pauses capture.
Publishing is bounded; recording does not upload ride samples to the database.
Stop releases GPS, drains queued writes, persists pending state, then synchronizes.
Reload restores interrupted/pending state without silently claiming capture resumed.
Account changes stop capture; pending records retain their original owner.
Resume records a gap and clears the previous fix, avoiding invented gap distance.

Upload:
1. Upsert ride_sessions with stable id, owner, bike, started_at, recording status
   and client_sync_version=1; onConflict id, ignoreDuplicates true.
2. Send batches <=100. Map local row.id to client_sample_id; OMIT numeric server id.
   Upsert samples onConflict client_sample_id, ignoreDuplicates true. Delete local
   sample entries only after acknowledgement. Lost receipts retain original UUIDs.
3. Persist completionRequested before the completion call. Invoke complete_ride_v1:
   p_session_id UUID, p_ended_at UTC, p_duration_seconds Int,
   p_distance_miles, p_max_speed_mph, p_average_speed_mph numeric,
   p_end_lat/p_end_lng nullable Double, p_sample_count Int.
4. The invoker RPC checks authenticated ownership, bounded values, time/duration,
   synchronization version and acknowledged row count. It locks the ride, increments
   current bike mileage and finalizes the session in one transaction. Repeated
   completion returns the receipt without repeating mileage.
5. Only receipt {session_id: same ID, status: complete} permits local synced state.
   Failure leaves pending state. No fallback to separate odometer writes.

Discard is prohibited after completion was requested because the server may have
committed despite a lost response. Retry first. Recovery export contains metadata
and UNSYNCED local samples; acknowledged samples must be read from the server.
There is no recovery-import UI. Keep exports private: they contain location data.
Broad owner table-update grants still permit a user to edit their own mileage.
This is cooperative retry accounting, not a certified vehicle odometer ledger.
Old web builds use non-atomic separate mileage updates; move clients to this release
before claiming simultaneous old/new client completion is fully coordinated.

6. AUTH, PROVIDERS, STORAGE AND SAFETY
Implement invitation acceptance and password reset links via approved universal
links/custom schemes and Supabase redirect allowlists. Retain session refresh,
explicit sign-out, account-cache isolation and MFA requirements. Store session
material in Keychain, never UserDefaults or logs. Server/RLS is authoritative.
Use published Supabase Swift interfaces after checking their current documentation.
Do not trust editable user_metadata to grant privileges.

Provider APIs: inspect api/road-info.js, road-info-live.js, poi-nearby.js and
fuel-nearby.js plus server/ helpers. Preserve supported GET query names, decimal
coordinate bounds, bearer authentication where required, quota enforcement and
bounded provider timeouts. The browser wrapper rewrites only exact same-origin
road-info calls. Nearby places uses /api/poi-nearby with category. Fallback source
and unknown speed limits must be visible. Do not move paid secrets into Swift.
Use URLSession cancellation and structured provider errors; distinguish missing
configuration, authorization, quota, network outage and empty legitimate results.

Inspect Storage bucket privacy, object owner paths, MIME/size restrictions, signed
URL expiry, upload/delete policies and attachment metadata before native upload.
The inventory lists source bucket/path references, not verified deployed policy.
Do not assume a public URL is private or a private bucket is directly downloadable.

Hardware remains experimental/disconnected. No ECU writes, CAN/K-Line transmit,
simulated telemetry presented as live, emergency dispatch claims, or production
background recording promises. Preserve electrical isolation requirements in the
engineering baseline. GPS-derived lean/acceleration is not calibrated IMU truth.
Physical iPhone/Safari capture, suspension, screen lock and long ride performance
require actual device validation. Browser IndexedDB cannot prevent OS suspension
or survive user-cleared site data. Native Core Location background capture needs
explicit capability, permission, battery and lifecycle design.
